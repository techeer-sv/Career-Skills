# 포트폴리오 구조화 가이드

개발자 포트폴리오를 **"채용 담당자가 30초 안에 판단하고, 면접관이 파고들 거리를 찾는"** 문서로 구조화하는 원칙. `references/`의 스켈레톤을 채울 때 이 문서를 기준으로 삼는다.

---

## 0. 핵심 철학 — 증거로 증명하는 포트폴리오

- **주장이 아니라 증거.** "고성능/대용량/실시간" 같은 형용사는 감점 요인이다. 수치·그래프·표·커밋·PR로 대체한다.
- **모든 수치는 정합해야 한다.** 표지에 올린 값, 본문 표의 값, 대시보드 캡션의 값이 **같은 지표면 같은 숫자**여야 한다. 하나라도 어긋나면 전체 신뢰가 무너진다. (리뷰 관점: `hiring-sim-portfolio-review`의 정합성 감사)
- **본인 기여가 명확해야 한다.** 팀 프로젝트면 "내가 설계/구현/검증한 부분"을 분리한다.
- **깊이 > 개수.** 얕은 프로젝트 6개보다, 문제→해결→검증이 끝까지 있는 프로젝트 2~3개가 강하다.

---

## 1. 슬라이드 유형과 목적 (권장 예시 · 고정 아님)

> 고정 순서·개수가 아니다. 디자인 템플릿처럼 슬라이드를 **취사·복제·재배치**한다 — 한 프로젝트가 1장일 수도, 문제별로 여러 장일 수도. (구성 규칙은 SKILL Step 3)

| # | 슬라이드 | 목적 | 필수 |
|---|----------|------|------|
| 1 | **Cover** | 이름 + 대표 성과 3개 + 연락처. 30초 첫인상 | ✅ |
| 2 | **Introduce** | 나를 한 문장으로 규정 + 핵심 역량 키워드 | ✅ |
| 3 | **Project Overview** | 프로젝트 개요 + 대표 수치 + 아키텍처 | ✅ (프로젝트당) |
| 4 | **기술적 고민 (Concerns)** | "왜 이렇게 풀었는가" — 의사결정 품질 | ✅ (프로젝트당) |
| 5 | **성과 Deep-dive** | 개선 1건 = 1장. 표+문제/해결/결과+증거 | ✅ (개선당) |
| 6 | 부하테스트 Before/After | 표 + 해석 note + 대시보드 | 선택 |
| 7~9 | 문제 / 해결 / 성과 | 서사형 프로젝트(AI·리서치)용 대체 레이아웃 | 선택 |
| 10 | **Open Source / Public Proof** | 외부에서 검증된 기여 (PR 머지 등) | 선택 (강력 추천) |
| 11 | **ETC** | 기타 경력/활동 + 핵심 역량 요약 표 | 선택 |
| 12 | **Closing** | 감사 + 연락처 | ✅ |

> 프로젝트 배치 순서 = **가장 강한 프로젝트를 앞으로**. 채용 담당자는 끝까지 안 볼 수 있다.

## 2. 슬라이드별 작성 원칙

### Cover (표지)
- **대표 성과 3개**는 포트폴리오 전체에서 가장 임팩트 있는 Before→After 수치. 반드시 본문에서 다시 증명된다.
- 태그라인은 "직무 + 차별점" 한 줄. 예: `MSA · Event-Driven · 이벤트 정합성/장애 복원 파이프라인`.

### Introduce
- **한 문장 규정**: "단순 CRUD가 아니라 X를 수치로 증명하는 Y 엔지니어" 형태로 정체성을 못 박는다.
- **pill 4개**: 핵심 역량(굵게) + 근거 기술(작게). 뒤 프로젝트에서 전부 회수된다.

### Project Overview
- 첫 줄에 **대표 수치 4~5개**(mcard)를 깔아 "이 프로젝트가 무엇을 증명하는지" 즉시 보여준다.
- Tech Stack은 **실제로 쓴 것만.** 안 쓴 기술을 넣으면 정합성 감사에서 걸린다.
- 아키텍처 다이어그램은 필수. 없으면 그려서라도 넣는다.

### 기술적 고민 (Concerns) — 가장 중요한 차별화 슬라이드
- 각 항목: **문제 상황 → 대안 → 선택 근거 → 트레이드오프 → 결과 수치**.
- 채용 담당자가 가장 보고 싶어하는 건 "왜?"다. 기술 나열이 아니라 **의사결정**을 쓴다.
- 강조하고 싶은 1~2개는 `concern wide`로 크게.

### 성과 Deep-dive (핵심)
- **1개 개선 = 1장.** 여러 개선을 한 장에 몰지 않는다.
- 왼쪽 **표**(Before/After 수치) + 오른쪽 **문제/해결/결과 trace** + 하단 **증거 이미지 + 캡션**.
- **문제**(현상·원인) → **해결**(핵심 기법 한 줄) → **결과**(측정된 개선). 각 1~3문장.
- 캡션은 "무엇을 어떻게 측정했고, 이미지에서 무엇이 보이는지"를 설명한다. 이미지가 스스로 말하게.

### Open Source / Public Proof
- 토이 프로젝트로 증명 안 되는 것 = **처음 보는 대규모 코드베이스에서 안전하게 변경하고 리뷰·CI를 통과**한 경험.
- Merged / In Review로 나누고, 각 PR은 **한 줄로 "무엇을 왜 고쳤는지"**.

### ETC / 핵심 역량 표
- 오른쪽 **역량 = 기술 = 검증** 3열 표가 포트폴리오 전체의 요약. 각 행의 "검증"은 앞에서 나온 수치로 회수한다.

## 3. 수치·증거 규율 (체크리스트)

- [ ] 표지 대표 수치가 본문 표에서 **동일 값**으로 다시 나오는가?
- [ ] 같은 지표가 표·그래프·캡션에서 **단위(ms/s, 건/초)와 값이 일치**하는가?
- [ ] "평균"이라 쓰고 실제 p95/p99를 쓰지 않았는가? (백분위 혼용 금지)
- [ ] 평균/전체 처리량이 피크보다 크게 적혀 있지 않은가? (산술적 불가능)
- [ ] "개선"이 실제로는 **측정 대상 바꿔치기**가 아닌가? (예: 접수시간을 처리시간처럼)
- [ ] 플레이스홀더·TODO·빈 그래프가 남아 있지 않은가?
- [ ] 팀 프로젝트에서 **본인 기여**가 분리되어 있는가?
- [ ] Tech Stack에 실제로 안 쓴 기술이 없는가?

## 4. 디자인 시스템 (레퍼런스 공통)

`references/*.html`은 **디자인 무드만 다르고 슬라이드 골격·플레이스홀더 규칙은 공유**한다. 새 슬라이드를 추가할 때도 규칙을 지킨다.

- **슬라이드 블록 (고정 세트 아님)**: 표지 · 목차 · 경력 타임라인 · 프로젝트 개요 · 프로젝트 상세 · 성과 지표 · 성능 비교 · 트러블슈팅 · 교육·자격·수상 · 마무리. 디자인 템플릿처럼 `<section>`을 **복제·삭제·재배치**해 자료에 맞춘다.
- **테마색**: 각 레퍼런스는 `--accent` 한 변수로 강조색을 바꾼다. 개선(좋아짐) 수치는 초록(`.down`), 악화/기준선은 일반 텍스트, 문제/경고는 주황 톤.
- **플레이스홀더**: `[대괄호]`=사용자 교체값, 샘플 문구·수치=톤 예시(교체 필수), 이미지 자리=안내 라벨 카드(`--guide-display`로 토글). 각 `<section>`의 `data-speaker-notes`=채우기 지침.
- **표**: `.table-card > table.compact`. **한글 줄바꿈**: `word-break: keep-all`로 어절 단위 줄바꿈.
- **특수 디테일은 레퍼런스에 심지 않는다.** 도메인 특화 슬라이드·별난 레이아웃은 사용자 요청으로 별도 제작(레퍼런스는 톤 기준일 뿐).

---

## 5. 출력물 규칙

- 결과는 **자기완결적 단일 HTML** (CSS·JS 인라인)로 만들면 공유/PDF 변환이 쉽다.
- 이미지는 상대경로(`./assets/...`)로 분리하고, 안내 라벨 카드를 실제 캡처로 교체한다.
- 브라우저에서 열어 **슬라이드 미리보기 · 키보드 ←→ / 휠 네비게이션 · 레이아웃(오버플로)**을 확인한다.
